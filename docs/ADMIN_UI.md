# Игровая админ-панель MRE

## Назначение

`MreAdminMenu` предоставляет игровые UI-маршруты для player-usable административных действий MRE. В обычном сценарии персоналу не нужно вводить команды в чат. Кнопка запуска панели доступна при `mre.admin` или `mre.staff`; резервный `/admin` требует `mre.admin`. Серверные сервисы повторно проверяют actor, сессию и точное разрешение на каждом действии. Панель не исполняет текстовые команды, не задаёт actor/SteamID из клиента и не выдаёт права.

Вкладки панели: **Игрок**, **Режимы**, **Объект**, **Мир и выдача**, **Профили и модерация**, **Инвентарь и события**.

## Каталог действий и разрешения

Все 22 действия `AdminPolicy` имеют UI-маршрут. Каждое из них дополнительно требует `mre.admin.<action>`; `players` управляет списком подключённых игроков, а `announce` — публикацией объявлений.

| Действие | UI |
|---|---|
| `players` | Список подключённых игроков с выбором цели и страницами |
| `tp`, `bring`, `heal`, `kick`, `spectate`, `freeze`, `kill` | Вкладка «Игрок»; kick и kill требуют подтверждения/повторной проверки цели; лечение себя доступно отдельно |
| `save`, `day`, `night`, `announce` | Вкладка «Мир и выдача»; событие или объявление о плановом перезапуске (сам сервер не перезапускается) |
| `fly`, `freecam`, `god`, `vanish`, `workzone`, `stats` | «Режимы»; переключатели включают и выключают состояние, скорость MreFlight задаётся отдельно |
| `owner`, `door`, `storage`, `remove` | «Объект»; действия применяются к объекту под прицелом, `remove` требует подтверждения |

`/give` и `/veh` вынесены в числовые контролы `MreAdminTools`; требуют `mre.admin` и соответственно `mre.admin.give` или `mre.admin.veh`. Предмет можно выдать себе или выбранному подключённому игроку. Транспорт появляется рядом с администратором. MreFlight и объявления вызывают typed API напрямую.

Вкладка «Профили и модерация» покрывает все 13 операций `/staff`: `list`, `profile`, `history`, `logs`, `note`, `warn`, `commend`, `kick`, `ban`, `mute`, `unban`, `unmute`, `revoke`. Требуются `mre.staff` и отдельный `mre.staff.<action>`; это разрешения не зависят от `mre.admin`. Поиск профилей, история и журнал листаются кнопками навигации; для просмотра/действия по отключённому игроку введите его SteamID64. Ban/mute принимают `30m`, `2h`, `7d` или `perm`. Каждая новая модерационная операция получает GUID, повтор того же UI callback переиспользует тот же operation ID; сервер API остаётся источником авторизации и идемпотентности. Отзыв ban/mute также проверяет соответствующее право `unban`/`unmute` и не снимает чужой native-бан.

Вкладка «Инвентарь и события» предоставляет осмотр и страницы снимков смерти через `MreInventoryAudit`, ручной запуск аирдропа и просмотр его состояния через `MreAirdrop`. Инвентарь требует `mre.admin` и соответствующее `mre.inventory.inspect`, `mre.inventory.deaths` или `mre.inventory.restore`; ручной аирдроп требует native admin либо `mre.airdrop.admin`. Для компенсации вводится стабильный `SnapshotId`, сервер показывает предпросмотр на 30 секунд и после одноразового подтверждения выдаёт вещи снимка в свободные слоты. Лут на месте смерти не удаляется; если инвентарь цели не вмещает весь набор, компенсация не выдаётся.

## Персональные группы доступа

Проектная иерархия Rocket — `helper` → `moderator` → `senior_moderator` → `mre_admin` → `head_admin` → `mre_owner`; наборы nodes заданы в `config/RocketPermissions.xml` и описаны в [STAFF_GROUPS.md](STAFF_GROUPS.md). Интерфейс не определяет полномочия по имени/приоритету группы: он запрашивает и проверяет точные nodes каждого действия. Поэтому Helper видит разрешённый список игроков и свои staff-операции, Moderator получает добавленные ему kick/mute действия, старшие роли получают только nodes, назначенные им конфигурацией. Разделы без доступных операций скрываются, а недоступные кнопки/поля скрываются; серверные API повторно проверяют права при вызове.

Вкладка админки и `AdminPolicy`-действия проверяют `mre.admin` вместе с `mre.admin.<action>`; `freecam` использует `mre.admin.fly`. Выдача и транспорт проверяют свои nodes `mre.admin.give`/`mre.admin.veh`. Staff-функции используют отдельную пару `mre.staff` + `mre.staff.<action>` и не требуют `mre.admin`. Инвентарные действия требуют базовый `mre.admin` и точный `mre.inventory.*`; аирдроп использует `mre.airdrop.admin` отдельно. Конфигурационная иерархия — проектное решение, а не подтверждение фактически применённых групп runtime-сервера: при текущей проверке runtime всё ещё содержит прежнюю одиночную staff-группу `mre_admin`. Native Admin Unturned обходит Rocket permission checks в используемых сервисах, поэтому он не подходит для проверки ролевого разграничения.

## Границы

- UI напрямую вызывает типизированные API. Резервные `/admin` и `/staff` могут оставаться доступными, но панели не требуется писать в чат.
- Команда `/whenairdrop` — публичная информация о расписании, а не административное действие. Восстановительная `restorehomes` остаётся console-only операцией техобслуживания.
- Панель не заменяет клиентскую доставку Effect bundle. Ввод полей использует `EffectManager.onEffectTextCommitted`; игрок и текущая сессия берутся из серверного callback.
- Ручной аирдроп не переносит расписание. После неоднозначного результата оператор проверяет статус, а не повторяет запуск автоматически.
- `mre.admin` не раздаётся донатным группам. Разрешения `mre.staff.*`, выдачи, восстановления и аирдропа следует назначать только доверенным группам по принципу минимальных полномочий.

## Сборка

Соберите исходники в указанном порядке, чтобы compiler references панели совпадали с используемыми API:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Build-MreInterface.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Build-MreFlight.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File src/MreAdminTools/Build.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Build-MreModeration.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Build-MreInventoryAudit.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Build-MreAirdrop.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File src/MreAdminMenu/Build.ps1
```

Сборщик панели проверяет staged DLL и их SHA-256 по `build-manifest.json`, затем фиксирует хэши всех compiler references в своём manifest. Он не устанавливает DLL. Effect bundle собирается отдельно через Unity 2022.3.62f3 в меню `MRE → Admin → Собрать Windows bundle`; для него нужна действующая лицензия Unity и доставка клиенту.

## Статус приёмки

Compile-only сборка подтверждает только компиляцию серверного кода. На текущем этапе UI bundle не собран/не доставлен клиенту, поэтому запуск в игре не подтверждён. Требуется сборка клиентского Effect, установка только после проверки полного набора DLL и ручная приёмка: права каждой группы, отзыв права во время сессии, действия по онлайн/offline SteamID, повторы модерации, сроки и снятие MRE наказаний, стабильный SnapshotId, полное/неполное восстановление, ручной аирдроп и отображение панели у чистого клиента.
