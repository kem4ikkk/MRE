# Безопасная сортировка вещей MRE

Состояние на **01.11.2026**, Europe/Moscow. Собственный MIT-плагин `MreInventorySort 0.1.0.0`. Исходники и сборщик подготовлены, **на сервер не установлен**. `Enabled=false` по умолчанию: включение требует независимого review Sol и отдельной приёмки с игровыми клиентами на копии экземпляра.

## Команды и API

| Команда | Действие | Право |
|---|---|---|
| `/sort` или `/sort inventory` | Личные страницы 2–6, каждая отдельно; рука должна быть пустой, действие завершено | `mre.sort` |
| `/sort storage` | Только текущее открытое разрешённое обычное хранилище | `mre.sort` |

Оружейные слоты 0/1, надетая одежда, временная область подбора, другие игроки и закрытые контейнеры не сортируются. Содержимое рюкзака/жилета/рубашки/брюк упорядочивается внутри своей страницы; надетый предмет одежды не снимается. Для storage оружие в руке само по себе не является запретом: перемещаются только вещи контейнера, а не оружие. Между вызовами действует пауза 2 секунды.

Публичный API на игровом потоке: `MreInventorySortPlugin.Instance`, `CanSortInventory(actor)`, `CanSortStorage(actor)` и `Sort(actor, bool storage)`, возвращающий русское сообщение. `Instance` может быть `null`. UI передаёт настоящего actor из серверного события, не SteamID из клиентского сообщения. API повторяет проверку сессии, права, доступности и выбранного контейнера перед изменениями. Эти методы не являются готовыми кнопками инвентаря.

## Что именно изменяется

Сначала строится полный план для всех выбранных страниц без изменения игры: тип предмета, ID, качество и количество задают порядок; одинаковые записи сохраняют исходный взаимный порядок. Каждая вещь размещается слева направо, сверху вниз. Поворот остаётся прежним. Стопки не объединяются, количество не нормализуется, между страницами вещи не переносятся. Если новый порядок не помещается, операция полностью отклоняется.

Применение изменяет только `ItemJar.x/y` уже существующих jar. Не создаёт новые `Item`, не извлекает их из серверного списка, не вызывает `removeItem`, `addItem`, `tryAddItem`, `forceAddItem`, drop или RPC приёма клиентского drag. Исходные jar/Item, ID, amount, quality, state и rot проверяются до и после перестановки. Пересборка сетки выполняется нативным `Items.loadSize` с прежними размерами. Она разрешена только после проверки, что все исходные и итоговые прямоугольники находятся в границах и не пересекаются: выход за границу мог бы вызвать нативный discard.

Подписки других плагинов не снимаются и не подменяются. События добавления/удаления предметов не вызываются: существование вещей не меняется. Система обновляет нативный inventory update index; для обычного storage вызывает нативный `rebuildState`. Сторонние плагины, рассчитывающие координаты исключительно по add/remove hooks, должны пройти отдельную проверку совместимости. `Items.loadSize` может заменить внутренний объект списка, сохраняя все jar и Item; код, сохраняющий ссылку на старый список, также требует проверки.

Операция синхронна на игровом потоке, без ожидания, coroutine и фоновых перестановок. Перед изменением повторно сверяются размеры, ссылки страниц и полный снимок. Повторный вызов того же игрока блокируется. Живой объект игрока должен совпадать с актуальным `PlayerTool.getPlayer`.

## Доступ к хранилищу

Плагин не открывает контейнер и не меняет владельца или блокировку. Одновременно обязательны:

- `isStoring=true`, та же `inventory.storage`, `isOpen=true`, `opener` равен actor, а `inventory.items[STORAGE]` является тем же объектом, что `storage.items`.
- Контейнер открыт ровно одним подключённым игроком; actor жив и его текущая сессия не заменена.
- Нативный `checkRot(actorId, groupId)` разрешает доступ с учётом закрытого замка, владельца и ненулевой группы. В отличие от `checkStore`, эта проверка не отвергает уже открытый контейнер только из-за `isOpen`.
- Контейнер активен, доступен для взаимодействия, находится в настоящем barricade drop на расстоянии не более 20 м, линия взаимодействия не перекрыта.
- Это штатные `InteractableStorage` и `Items`, без `onStateRebuilt` стороннего виртуального склада.

Багажники, витрины, виртуальные склады, подклассы с неизвестными инвариантами и чужой locked storage, открытый административным обходом, получают отказ. Это явные ограничения первой реализации; общий запрос «все хранилища» не считается подтверждённым для этих случаев.

## Синхронизация и ошибки

После проверки серверной раскладки отправляются только проверенные нативные reliable server→owner операции `sendItemRemove(byte,ItemJar)` и `sendItemAdd(byte,ItemJar)` через reflection по точной сигнатуре. Сначала удаляются старые координаты **на клиенте**, затем публикуются текущие jar. Прямой вызов `ReceiveItemRemove` на сервере не используется. Состав серверных вещей остаётся полным на всём протяжении отправки. Повторная отправка initial inventory/storage без очистки непригодна: соответствующий клиентский обработчик добавляет записи, не гарантируя очистку прежних.

При ошибке возвращаются исходные координаты, пересобирается сетка и повторно сохраняется storage. Метаданные никогда не восстанавливаются поверх неизвестного изменения другим плагином. Для клиентского отката очищается объединение старых и возможных новых координат и публикуется исходное состояние. Закрытому или отключённому клиенту содержимое storage не отправляется. При постоянной сетевой ошибке или неподтверждённом откате сортировка блокируется до сверки/перезагрузки плагина; клиенту предлагается переподключение. Это не обещание автоматического восстановления после любой аварии Unity, памяти, чужого асинхронного плагина или изменения контейнера.

Ванильные drag/drop запросы используют координаты без версии раскладки. Запрос, отправленный клиентом непосредственно перед сортировкой, может относиться к прежним координатам. Без отдельного клиентского протокола нельзя обещать сохранение намерения такого drag/drop; этот сценарий обязательно проверяется в игре. Привязки клиентской панели быстрого доступа и их восстановление после remove/add пакетов тоже пока не подтверждены. На действующих вещах плагин ради тестирования не включается.

До мутации отклоняются неизвестные assets, изменения размеров jar, world-linked jars, повторные ссылки Item/jar, пересечения, предметы за границей, больше 200 предметов на странице, поле state больше 255 байт и сетки площадью больше 4096 клеток. Поиск ограничен 500000 попытками на страницу.

## Сборка и выполненные проверки

```powershell
.\scripts\Build-MreInventorySort.ps1
dotnet run --project src/MreInventorySort/Tests/MreInventorySort.Tests.csproj --configuration Release
```

Результат: `runtime/builds/MreInventorySort/MreInventorySort.dll`, `build-manifest.json`. Build не устанавливает и не запускает плагин. Manifest содержит hashes DLL, исходников и references. Сборка внедряет hash использованной `Assembly-CSharp.dll`; при несовпадении DLL игры или отсутствии private RPC API сортировка остаётся недоступной. После обновления игры нужны повторный аудит, сборка и приёмка, а не только правка конфигурации.

**Выполнено:** настоящая компиляция по установленным U3DS/Mono/Rocket DLL; **28 сценариев PASS** на фактических `SortCore.cs` и `NativeSortSurface.cs`. Границы Unity/API заменены дублёрами. Покрыты план, непомещающийся порядок без изменений, metadata/identity/rotation/нулевое количество/255-byte state, повторные ссылки, invalid bounds, grid failure, transient/permanent send failure, storage persist failure, многостраничный откат, неизвестные hooks, запрет перезаписи чужих metadata, close во время отправки, пустые страницы и порядок native packets. Временные outputs находятся только в `runtime/builds/MreInventorySort`.

**Не выполнено:** независимое review Sol, загрузка этого плагина сервером, реальный ввод команды, пустая рука/клиентский UI, штатные permissions и locked/public/group storage в живой игре, Unity callbacks, сетевой порядок/повтор packets, queued drag/drop, hotbar, смерть/close/disconnect, save→restart→restore на настоящем контейнере и совместимость со всеми другими плагинами. Harness не подменяет эти проверки. Нужна копия экземпляра и два клиента, без изменения рабочих миров.

## Первичные источники

Прочитаны 31.10–01.11.2026; публичная `main` может измениться. Сигнатуры также проверены в фактической установленной DLL, а окончательная совместимость ограничена её hash.

- [SDG Items.cs](https://github.com/SmartlyDressedGames/U3-SDK/blob/main/Assets/Runtime/Assembly-CSharp/Unturned/Inventory/Items.cs): хранение jar, реконструкция сетки, callbacks и риск discard при нарушенных границах.
- [SDG PlayerInventory.cs](https://github.com/SmartlyDressedGames/U3-SDK/blob/main/Assets/Runtime/Assembly-CSharp/Unturned/Player/PlayerInventory.cs): native drag, сетевые add/remove, открытие storage и первоначальная синхронизация.
- [SDG InteractableStorage.cs](https://github.com/SmartlyDressedGames/U3-SDK/blob/main/Assets/Runtime/Assembly-CSharp/Unturned/Interactable/InteractableStorage.cs): lock/owner/group, opener, реальное сохранение и hooks виртуального storage.
- [SDG ItemJar.cs](https://github.com/SmartlyDressedGames/U3-SDK/blob/main/Assets/Runtime/Assembly-CSharp/Unturned/Inventory/ItemJar.cs) и [Item.cs](https://github.com/SmartlyDressedGames/U3-SDK/blob/main/Assets/Runtime/Assembly-CSharp/Unturned/Inventory/Item.cs): позиции, поворот, размеры и метаданные. Код SDK использован как справочник и в новый плагин не скопирован.
