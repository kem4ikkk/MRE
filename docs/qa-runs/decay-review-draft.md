## Подтверждённое поведение

- `DecayModel`, `ProtectionSearch`: владелец либо общая ненулевая группа; радиус 50 м включительно в 3D; безопасное поведение при неизвестных входах. Сейф останавливает гниение, ремонт требует своего работающего генератора и отсутствия рейд-блока. Неизвестный кандидат в полном списке запрещает весь расчёт — консервативно, но потенциально останавливает мир из-за одного повреждённого объекта.
- `FractionalHealth`: сотые HP накапливаются раздельно для ремонта и урона, целые HP ограничены 0/max; 0 HP не воскресает. Малое max корректно обрабатывается через остатки; арифметика ushort помещается в int.
- `RaidBlock`: использует owner/group объекта, а не список подключённых игроков; модель допускает offline owner. Повторный удар продлевает 600 секунд; Capture/Restore переносит оставшееся время, не вычитая выключенный сервер. Реальных игровых событий и полноты охвата модель не проверяет.
- `StepEngine.Prepare`: отклоняет неполный снимок целиком, не мутирует переданные объекты; FakeGame отклоняет повторы и устаревшую ревизию в пределах процесса. RuntimeGate требует все признаки evidence и не начисляет простой после рестарта; неизвестный исход commit блокирует экземпляр.
- `PolygonZone`: проверяет простоту полигона, конечность, повторы, нулевую площадь; граница включена. Инструмент карты использует реальный CartographyVolume и хеши, а импорт требует точный набор точек. Экспорт маркирован DRAFT. Сервер инструмента только читает карту, слушает localhost и не применяет JSON к игровому миру.

## Блокеры до включения

1. **Crash persistence отсутствует.** Нет файлового хранилища, журнала транзакций, устойчивого ID объектов и согласованного commit HP/остатков/шага с сохранением U3DS. Повтор шага после рестарта FakeGame не предотвращает.
2. **Max-health migration не обеспечивается StepEngine.** Prepare восстанавливает FractionalHealth из текущего `b.MaxHealth`, но Building не содержит сохранённого max. Смена max между шагами не обнаруживается автоматически вопреки требованию FRACTIONAL_MODEL. Нужен persisted max/asset-version и проверка в адаптере либо расширение snapshot. Прямой вызов Apply обнаруживает смену max только внутри одного экземпляра FractionalHealth.
3. **Нет игрового адаптера.** Не подтверждены перечисление всех регионов и offline построек, owner/group при отсутствии игрока, актуальность group, события фактического player-caused урона, исключение гниения и отменённого урона из рейда, порядок применения с конкурирующим уроном/ремонтом. Нужна самостоятельная проверка рейда на offline owner и группу; существующий Teleportation block этим доказательством не служит.
4. **Зоны не приняты.** Нет подтверждённого набора границ всех 21 точек и игровых проверок на обеих сторонах границы. Успешная проверка проекции/формата не доказывает географический охват. HUD пока не доказан на клиенте с той же геометрией.
5. **Сейфы — эксперимент.** В старом `%TEMP%/mre-safe-u3ds-isolated/Logs/Server_SafeTest.log` строки 219–221 подтверждают загрузку TEST Safe 100/200/300 как Storage Item и предупреждение `animation clips list is empty` у всех трёх. Это доказывает серверную загрузку ассетов, но не размещение, доступ, физику, сетки, хранение предметов, клиентскую доставку и сохранность после restart/restore. ### Дополнение: race журнала и отдельный Canvas

У DurableJournal нет блокировки на весь Read → Write. При нескольких писателях возможен сценарий: A и B читают committed sequence=0; A публикует pending sequence=1; после завершения A писатель B создаёт уже освободившийся .tmp и заменяет основной файл своим pending sequence=1. FileMode.CreateNew защищает только одновременное существование .tmp, а не чтение-проверку-публикацию как одну операцию. Первый intent может быть потерян. Следовательно, это заготовка строго для одного последовательного писателя; до реальной интеграции требуется обеспечить/проверить этот контракт и запрет второго процесса. Существующие 44 теста гонку не покрывают. Pending-state после kill блокируется консервативно, но восстановление общего мира остаётся ручной неподтверждённой операцией.

Проверены `src/MreDecayZoneHud/HintPolicy.cs`, Unity builder и README. `dotnet run --project tests/MreDecayZoneHud/MreDecayZoneHud.csproj --configuration Release`: **PASS**. Unknown item/нет игрока скрывают панель; unknown zone даёт отдельный неопределённый статус и не выдаёт обычную зону. Если механика ещё выключена, будущий адаптер не должен вызывать подтверждённый 1%/2% статус только по геометрии: policy не имеет параметра operational readiness, это внешнее обязательство. Также внешними остаются классификация HousingPlanner/BuildingPart и очистка старого эффекта при выключении модуля/потере данных.

Canvas изолирован от действующего prefab, имена DecayZonePanel/Text не пересекаются с просмотренными узлами MreHud, CanvasGroup.blocksRaycasts=false и raycastTarget=false не должны перехватывать мышь. ### Durability: что исправлено

- `DurableJournal` удерживает `.lock` с `FileShare.None` весь срок жизни экземпляра. Второй экземпляр и отдельный процесс отклоняются тестами. Вызовы одного экземпляра сериализованы `lock(sync)`, поэтому прежняя гонка Read → Write закрыта для штатных пользователей этого класса на одном локальном пути. После конфликтующего Begin экземпляр блокируется консервативно.
- `ownedIntent` разрешает Commit только экземпляру, записавшему Begin. Новый экземпляр после прерывания не может подтвердить чужой pending intent; Load также его отклоняет. `Dispose` освобождает handle и инвалидирует экземпляр; оставшийся файл `.lock` не означает продолжающуюся OS-блокировку.
- `StateCodec` уже существует: версия, цикл и активные секунды, остаток 300-секундного цикла, объектные kind/instanceID/assetID/GUID/max/дробные остатки и owner/group raid remaining. Проверяются дубликаты ключей, диапазоны, пустые GUID, размеры списков, обрезанные данные и хвост. Прежнее утверждение об отсутствии схемы теперь устарело. Устойчивость игровых ID эта структура не доказывает.
- Путь журнала сейчас разрешён только внутри TEMP; это дополнительное ограничение изолированного прототипа. Это не готовое хранилище серверного runtime.

Прочитаны и выполнены оба сценария: nested Save внутри Apply не вызывает save delegate и даёт false внешнему Apply; nested Apply внутри Save не повторяет apply и даёт false внешнему Save. После обоих Dispose и новый IsolatedPendingStore не открывают оставленный pending. Первичные replay/reentrancy замечания в этих ветках закрыты.

Этот backend является репетицией отказа, а не успешным checkpoint: публикации состояния и независимого anchor намеренно нет, любой полностью дошедший путь оставляет pending. SaveAndVerifyWorld проверяет лишь ответ delegate и возможность прочитать fingerprint двух файлов, а не корректность нового мира относительно proposedState или долговечность Unity save. Delegates являются доверенным кодом и сами не ограничены TEMP этой обёрткой; путь fingerprint ограничен TEMP, но это не sandbox произвольных delegate. Quiescence, полный мир, идентичность объектов и разрешение неопределённого результата остаются внешними недоказанными условиями. Тесты используют маленькие искусственные файлы и последовательные ошибки, не падение U3DS/ОС. Backend к рабочему миру не подключён; успешного согласованного commit или восстановления он не подтверждает.
