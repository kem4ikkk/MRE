# Локальное обслуживание MRE

Дата: 29.10.2026. Скрипты рассчитаны на Windows PowerShell 5.1 и локальную установку в `runtime/server`. Игровые файлы, резервные копии и секреты не включаются в Git.

## Перед копированием и восстановлением

Выполнить `scripts/Stop-MreServer.ps1` и дождаться завершения процесса. Он передает Save и Shutdown через локальный мост. Скрипты не завершают Unturned принудительно. Они отказывают, если найден работающий `Unturned.exe` из `runtime/server` или невозможно определить путь одного из процессов Unturned. Обычный клиент с известным путем вне каталога сервера не мешает операциям.

Запуск MRE и операции обслуживания должны совместно использовать эксклюзивный lock `runtime/.mre-maintenance.lock` с `FileShare.None`. Само существование файла lock не означает занятую блокировку. Во время операций нельзя запускать сервер вручную в обход согласованного стартового скрипта. Процессная проверка выполняется повторно, но ручной запуск не обязан соблюдать файловую блокировку.

## Резервная копия остановленного экземпляра

Из корня проекта:

```powershell
.\scripts\Backup-MreServer.ps1
```

Можно указать уникальное имя из латинских букв, цифр, дефисов и подчеркиваний:

```powershell
.\scripts\Backup-MreServer.ps1 -Name MRE-before-update
```

Скрипт создает `backups/<имя>.zip` и `backups/<имя>.zip.manifest.json`. ZIP содержит **весь** `runtime/server/Servers/MRE`, в том числе сохранения, конфигурации и локальные данные Rocket-плагинов, находящиеся внутри этого каталога. Манифест содержит SHA256 архива и каждого файла, размеры и время UTC. Состав и хеши проверяются до публикации архива. Имена существующих копий не перезаписываются.

Неудачная операция может оставить `.partial` — такой файл не является законченной копией. Готовый ZIP без его манифеста также нельзя использовать этим восстановителем. Хеши выявляют повреждение; они не заменяют подпись и не делают неизвестный архив доверенным.

**Граница копии:** внешняя MySQL, данные плагина вне `Servers/MRE`, модуль LDM и серверная программа не входят. В текущем U3DS Workshop находится внутри `Servers/MRE/Workshop` и поэтому **входит** в полную копию; это увеличивает размер архива. Отдельные `secrets` и `runtime/control` не копируются. Перед внешним хранилищем нужен согласованный экспорт БД. Копия на том же диске не защищает от его потери; ZIP/манифест нужно переносить в отдельное защищенное хранилище. В копии могут находиться токены и пароли, поэтому ее нельзя публиковать.

## Предварительная проверка восстановления

```powershell
.\scripts\Restore-MreServer.ps1 -ArchivePath .\backups\MRE-before-update.zip
```

Без `-Apply` выполняется проверка архива, манифеста, целевого пути и остановки сервера; игровые данные не меняются. Предварительный режим может создать служебный каталог `runtime` и открыть/создать файл lock. Архивы принимаются только из `backups` текущего проекта.

## Применение восстановления

```powershell
.\scripts\Restore-MreServer.ps1 -ArchivePath .\backups\MRE-before-update.zip -Apply
```

Порядок:

1. Проверить SHA256 ZIP и соответствие MRE-манифесту.
2. Отклонить выходящие пути ZIP, повторяющиеся имена, символические ссылки и неожиданные файлы.
3. Распаковать в отдельный `.restore-stage-*` внутри `backups`, проверить хеш каждого файла.
4. Повторно проверить остановку MRE.
5. Сохранить текущий каталог целиком в `backups/MRE-before-restore-*/MRE`; рядом записать манифест с хешами. Это страховочный исходный каталог, а не новый ZIP.
6. Переместить подготовленную копию на фиксированный путь `runtime/server/Servers/MRE`.

Если переключение не удалось после сохранения исходного каталога, скрипт пытается вернуть исходный каталог на прежний путь. Он не удаляет прежние данные и не чистит страховочные каталоги автоматически. При ошибке могут остаться подготовительные каталоги для разбора. Перед ручным откатом проверить остановку сервера и абсолютные пути; не использовать рекурсивное удаление на вычисленном пути.

Восстановление не запускает сервер. После него выполнить запуск штатным скриптом, проверить загрузку PEI, журналы плагинов, контрольные предметы и права. Старый мир вместе с более новым журналом покупок требует отдельной сверки; данный локальный ZIP сам по себе не решает согласованность внешних платежных систем.
